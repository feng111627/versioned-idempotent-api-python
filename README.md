# Versioned Idempotent API

一个演示「**API 版本演进 + 写入幂等 + 乐观并发控制**」的 FastAPI 服务。
重点不是资源本身，而是客户端在**并发重试**与**逐步升级版本**时，
服务端行为可预期、可解释。

## 运行

```bash
uv sync                       # 安装依赖
uv run python main.py         # 启动服务（http://127.0.0.1:8000）
uv run pytest                 # 运行全部场景测试并打印覆盖清单
```

交互式文档：启动后访问 `/docs`。

## 资源与版本

资源为 `documents`，字段：

| 字段 | v1 | v2 | 说明 |
| --- | --- | --- | --- |
| `id` | ✅ | ✅ | 资源标识 |
| `title` / `content` | ✅ | ✅ | 业务字段 |
| `version` | ✅ | ✅ | 资源版本号，整数，每次成功更新 `+1`，初始为 `1` |
| `update_count` | ❌ | ✅ | v2 兼容式新增字段 |

读取（`GET`）的响应体带有当前 `version`，该值用于后续写入的乐观并发校验。

## 一、写入幂等语义

所有写请求（`POST` / `PUT`）**必须**携带请求头：

```
Idempotency-Key: <客户端生成的唯一字符串>
```

服务端以该键为索引保存「请求指纹 + 首次响应」。指纹由
`HTTP 方法 + 路径 + 规范化 JSON 请求体` 做 SHA-256 得到。

| 情形 | 行为 | 响应 |
| --- | --- | --- |
| 首次请求 | 执行业务并落盘结果 | 正常状态码，`Idempotency-Replayed: false` |
| 同键 + **相同内容**重试 | **不再次执行业务**，原样回放首次的状态码与响应体 | 与首次一致，`Idempotency-Replayed: true` |
| 同键 + **不同内容** | 明确拒绝，提示键已被其他请求占用 | `409 idempotency_conflict` |
| 缺少幂等键 | 拒绝写入 | `400 idempotency_key_required` |

要点：

- **只生效一次**：重复提交不会创建第二份资源，也不会把版本多推进一次；
- **结果一致**：重试拿到的状态码、资源 `id`、`version` 与首次完全相同；
- **失败不落盘**：业务校验失败（404/409/428 等）不占用幂等键，客户端修正后
  用同一个键仍可成功（这些失败本身可安全重试）；
- 幂等键在**服务端全局唯一**，建议用 UUID，且其作用域不区分 API 版本，
  因此不要在不同请求之间复用。

### 并发重复提交

同一幂等键的并发请求按「键级锁」串行化：

1. 第一个拿到锁的请求执行业务并保存结果；
2. 其余请求阻塞等待，拿到锁后读取已保存的结果并回放。

因此并发重试不会出现重复生效或部分生效。存储层的「检查 + 变更」在同一把
全局锁内完成，乐观并发控制也不存在 check-then-act 竞态。

## 二、并发冲突处理（乐观并发控制 OCC）

更新已有资源使用 `PUT`，并通过标准 `If-Match` 请求头携带**读取到的版本号**：

```
PUT /api/v2/documents/{id}
If-Match: 1
Idempotency-Key: ...
```

服务端比较 `If-Match` 与资源当前版本，据此把三类问题明确区分：

| 情形 | 状态码 | 错误码 `error.code` | 含义 |
| --- | --- | --- | --- |
| 版本匹配 | `200` | — | 更新成功，`version` 递增 |
| 版本过期/不匹配 | `409` | `version_conflict` | 资源已被他人改过，**拒绝而非静默覆盖**；响应信息中给出当前版本 |
| 未携带版本 | `428` | `version_required` | 缺少 `If-Match`，要求客户端先读再写 |
| 资源不存在 | `404` | `not_found` | 目标 id 不存在 |
| `If-Match` 非法（非正整数） | `409` | `version_conflict` | 版本格式无法识别 |

典型的「读—改—写」重试模式：

1. `GET` 取得资源与 `version`；
2. 带上 `If-Match: <version>` 提交 `PUT`；
3. 收到 `409 version_conflict` 时，重新 `GET`、合并变更后用新版本重试。

被拒绝的写入不会落盘，资源版本与内容保持不变。

错误响应体为统一形状：

```json
{ "error": { "code": "version_conflict", "message": "版本冲突：资源当前版本为 2，请求携带的版本为 1" } }
```

## 三、API 版本兼容策略

版本通过 URL 前缀区分：`/api/v1`、`/api/v2`。

### v1：已弃用，但继续可用

v1 的每个响应都显式携带弃用信号（基于 RFC 8594）：

```
Deprecation: true
Sunset: Sat, 31 Dec 2026 23:59:59 GMT
Link: </api/v2/documents/{id}>; rel="successor-version"
X-Api-Deprecated: v1; successor=v2
```

旧客户端无需立即改造，但应据此规划迁移。

### 兼容性规则

- **向后兼容扩展**：v2 只在 v1 基础上**新增**字段（`update_count`），
  不删除、不改变 v1 已有字段的含义；
- **v1 响应冻结**：新字段永远不会出现在 v1 响应中，旧客户端不会被意外破坏；
- **状态跨版本一致**：v1、v2 共用同一存储与同一套版本号。无论从哪个版本
  写入，另一版本立即可见，资源 `version` 同步单调推进。

### 未识别 / 不受支持的版本

不会默认回落到任一具体版本：

| 请求 | 响应 |
| --- | --- |
| `/api/v3/...`（含读/写） | `404 version_not_supported` |
| `/api`、`/api/`（未指定版本） | `404 version_not_supported` |

响应头 `Link` 会列出当前可用的文档入口，方便客户端发现受支持版本。

## 接口一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/v{1,2}/documents` | 创建（需 `Idempotency-Key`） |
| `PUT` | `/api/v{1,2}/documents/{id}` | 更新（需 `Idempotency-Key` 与 `If-Match`） |
| `GET` | `/api/v{1,2}/documents/{id}` | 读取（响应含 `version`；v1 带弃用头） |

## 测试与场景覆盖

`uv run pytest` 结束后会打印「场景覆盖清单」，列出每个场景及其用例与结果。
当前覆盖四类场景：

1. **写入幂等**：重复提交回放一致、同键异内容拒绝、并发创建/更新只生效一次、缺键拒绝；
2. **版本与乐观并发**：读取带版本、版本单调推进、过期版本拒绝、版本缺失/资源不存在区分、竞争更新一方成功；
3. **API 版本演进**：v1 弃用标记、v2 兼容扩展、跨版本状态/版本一致、未知版本与无版本路径明确报错；
4. **真实并发安全**：用 `asyncio` 直接并发驱动核心逻辑（绕过 TestClient 的单线程限制），
   验证 exactly-once 与竞争更新，并通过变异测试确认其确实能捕获竞态。
